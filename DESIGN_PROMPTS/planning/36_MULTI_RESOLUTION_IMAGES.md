# Feature 36 — 사진 다중 해상도 관리 (Multi-Resolution Image Pipeline)

## 1. 배경 및 문제 정의

포트폴리오 앱의 핵심 자산은 사진(이미지)이다. 현재 두 가지 업로드 경로가 존재한다.

| 경로 | 저장소 | 해상도 | 문제 |
|---|---|---|---|
| `POST /api/photos/upload` (파일 모드) | **로컬 디스크** (`uploads/`) | full(1080px) + thumb(400px 정방형 크롭) 2종 | Railway 컨테이너는 재배포/재시작 시 파일시스템이 초기화됨 → **업로드한 사진이 사라짐** (운영 치명 버그) |
| `POST /api/upload/image` (URL 모드 등 범용) | Supabase Storage | 원본 1종만 업로드 | 상세보기·목록·썸네일 모두 같은 원본을 내려받음 → 목록 화면에서도 수 MB 원본을 로드해 트래픽·로딩속도 손해 |

사용자 요청: 1024(상세/Retina) · 512(카드) · 256(목록) · 128(썸네일/어드민) 4단계 조합을 저장공간·성능·화질·**유지보수 비용** 균형을 고려해 구현.

## 2. 트레이드오프 검토

| 방식 | 저장 비용 | 응답 속도 | 유지보수 비용 | 채택 여부 |
|---|---|---|---|---|
| A. 업로드 시 4개 파일 실제 생성 + DB에 4개 URL 컬럼 저장 | 4배 저장공간 | 빠름(사전 생성) | 마이그레이션 필요, 스키마 4컬럼 증가 | ❌ |
| B. 원본 1개만 저장 + 요청마다 온디맨드 리사이즈 | 최소 저장공간 | 느림(매 요청 CPU) + 캐싱 인프라 필요 | Supabase 무료 플랜은 이미지 변환 미지원 → 직접 구현 시 서버 부하/캐시 서버 필요 | ❌ |
| **C. 업로드 시 4개 파일 실제 생성, DB는 기존 컬럼만 사용(`imageUrl`=1024, `thumbnailUrl`=256), 512/128은 파일명 규칙으로 응답 시점에 파생** | 4배 저장공간(사진은 용량 작아 무해) | 빠름(사전 생성, CDN 캐시 가능) | **DB 마이그레이션 0건**, 파생 로직 1곳(Java)에서 관리 | ✅ 채택 |

**채택 이유**: 저장 비용은 이미지 4장(합쳐도 원본 1장보다 작음)이라 무시할 수준이고, 응답 속도가 가장 중요한 이 앱의 특성(갤러리/탐색 화면 트래픽)에 맞다. 유지보수 비용은 "DB 스키마 변경 없음"이 핵심 — 새 컬럼·마이그레이션·프론트 재배포 없이 이름 규칙(`_1024.`, `_512.`, `_256.`, `_128.`)만 지키면 됨.

## 3. 아키텍처

```
업로드(멀티파트) → ImageVariantUtil.prepare()
                     ├─ 원본 검증(타입/크기)
                     ├─ 4단계 리사이즈(1024/512/256/128, 비율 유지, 크롭 없음)
                     └─ 256px 변형으로 색체학 분석(대표색/무드/팔레트) — 원본 대비 5배 이상 빠름
                   → SupabaseStorageService.uploadBytes() × 4
                     photos/{uuid}_1024.{ext}
                     photos/{uuid}_512.{ext}
                     photos/{uuid}_256.{ext}
                     photos/{uuid}_128.{ext}
                   → Photo 엔티티 저장: imageUrl=1024 URL, thumbnailUrl=256 URL (기존 컬럼 그대로 재사용)

응답(PhotoResponse) → imageUrl(1024), thumbnailUrl(256)에 더해
                       imageUrl512 / imageUrl128 을 ImageVariantUtil.deriveUrl()로 "계산"해서 추가
                       (DB에 저장하지 않음 — imageUrl 문자열 치환만으로 파생)

프론트엔드 → 화면 용도에 맞는 필드 사용
             상세/뷰어  → imageUrl (1024)
             카드/대표  → imageUrl512
             목록/미리보기 → thumbnailUrl (256)
             어드민 썸네일 → imageUrl128
```

## 4. 유저 스토리

- 작가로서, 사진을 등록하면 화면별로 적절한 크기의 이미지가 자동으로 제공되어 갤러리 로딩이 빨라지길 원한다.
- 방문자로서, 탐색 화면에서 스크롤할 때 큰 원본 이미지 때문에 느려지지 않기를 원한다.
- 운영자로서, 재배포해도 업로드한 사진이 사라지지 않기를 원한다 (로컬 디스크 저장 버그 수정 포함).

## 5. 수용 기준 (AC)

- [ ] `POST /api/photos/upload`로 업로드 시 Supabase Storage에 4개 크기(1024/512/256/128) 파일이 실제로 생성된다.
- [ ] 재배포 후에도 업로드한 사진이 정상적으로 보인다 (로컬 디스크 저장 제거).
- [ ] `PhotoResponse`에 `imageUrl512`, `imageUrl128` 필드가 포함되어 내려온다.
- [ ] 갤러리/탐색 목록 카드는 256px(`thumbnailUrl`), 상세 화면은 1024px(`imageUrl`)를 사용한다.
- [ ] 어드민 사진 목록(`AdminPhotosPage`)은 128px(`imageUrl128`)를 사용한다.
- [ ] 사진 삭제 시 Supabase Storage에서 4개 파일이 모두 삭제된다.
- [ ] 기존(레거시) 사진 데이터(로컬 디스크 경로 `/uploads/...`, 또는 URL 모드로 등록된 단일 URL)는 파생 실패 시 원본 `imageUrl`로 안전하게 폴백한다.
- [ ] DB 마이그레이션(ALTER TABLE) 없이 배포 가능하다.

## 6. 기술 결정 요약

- **DB 변경 없음** — `imageUrl`(1024), `thumbnailUrl`(256) 두 기존 컬럼만 사용.
- **512/128은 저장하지 않고 파생** — `ImageVariantUtil.deriveUrl(imageUrl, size)`가 유일한 진실 소스(backend), 프론트는 API 응답 필드를 그대로 사용(문자열 가공 로직 프론트엔드에 중복 없음).
- **파일명 규칙**: `{folder}/{uuid}_{size}.{ext}` — 이 규칙이 깨지면(레거시 데이터) 파생 함수가 원본 URL을 그대로 반환해 깨진 이미지 방지.

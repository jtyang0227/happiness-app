## 0. 한 줄 컨셉

> **"사진을 모아둔 곳이 아니라, 해낸 일을 보여주는 곳."**
> 포트폴리오의 기본 단위를 "사진 1장"에서 **"작업 1건(케이스)"** 으로 바꾼다.
> 방문자는 사진을 넘겨보는 대신 "이 작가가 *나 같은 의뢰*를 어떻게 해냈는지"를 읽고,
> 그 자리에서 **"이런 촬영 문의하기"** 로 넘어간다.

---

## 1. 배경 — 지금 포트폴리오에 없는 것

코드를 기준으로 현재 상태를 점검했다(2026-10-20).

**이미 충분한 것 (더 만들지 않는다)**
- 보여주는 형식: 템플릿 4종(Editorial/Scrl/Minimal/DarkRoom) + 준비 중 4종, 슬라이드쇼, 매거진 뷰어 7종 판형
- 신뢰 신호: 추천사·언론/수상·클라이언트 로고·가격 패키지·뉴스레터 섹션이 이미 TemplateEditorial에 연결됨
- 일 받기 동선: 문의 폼(`/inquiry/:profileName`), 예약 위저드(`/booking/:profileName`)

**비어 있는 것 — 컨셉의 공백**
1. **"맥락"이 없다.** 시리즈(`Series`)는 제목·설명·사진 묶음뿐이다. 누구를 위한 작업이었는지(개인/브랜드),
   어떤 유형의 촬영인지, 언제 했는지, 어떤 의도로 찍었는지가 데이터로 존재하지 않는다.
   그래서 템플릿을 아무리 바꿔도 결국 "예쁜 사진 그리드"로 수렴한다 — 경쟁 서비스(Instagram, Behance)와
   구분되는 이유가 없다.
2. **시리즈에 자기 페이지가 없다.** `TemplateEditorial`의 시리즈 카드는 클릭하면 썸네일 6장을 펼칠 뿐이다.
   링크로 공유할 수 있는 "작업 1건"의 주소가 없어서, 작가가 "웨딩 작업은 이걸 보세요"라고 보낼 곳이 없다.
3. **보여주기와 일 받기가 끊겨 있다.** 문의 버튼은 포트폴리오 전체에 하나뿐이고, 어떤 작업을 보고
   문의했는지 맥락이 전달되지 않는다. 문의 폼에서 고객이 촬영 유형을 다시 고른다.

**결론**: 형식(템플릿)이 아니라 **내용 구조(작업 단위의 맥락)** 가 컨셉의 빈자리다.

## 2. 컨셉 — 세 개의 기둥

| 기둥 | 의미 | 화면에서 보이는 것 |
|---|---|---|
| **① 작업 단위 (Case, not Photo)** | 시리즈를 "프로젝트 케이스"로 승격 | 케이스마다 고유 주소 `/portfolio/:profileName/work/:seriesId` |
| **② 맥락 (Context)** | 촬영 유형·클라이언트·시기·작업 이야기 | 케이스 상단 메타 줄 + "작업 노트" 본문 |
| **③ 이어지는 의뢰 (Next Commission)** | 본 작업과 같은 유형으로 바로 문의 | 케이스 하단 "이런 촬영 문의하기" — 촬영 유형이 미리 선택된 문의 폼 |

**톤**: 작가 노트/전시 캡션. 과장된 마케팅 문구가 아니라 "누구와, 무엇을, 왜 이렇게 찍었는지"를
짧고 담백하게. Toss 플랫 디자인 위에서 사진을 크게, 글은 좁은 컬럼(최대 640px)으로.

## 3. 페르소나

- **작가 — 김하늘 (31, 웨딩·프로필 프리랜서)**: 인스타 DM으로 문의를 받는데 매번 "웨딩 작업 더 볼 수 있을까요?"
  라는 질문에 사진을 일일이 보낸다. *원하는 것*: 작업 유형별로 링크 하나씩 보내고 끝내기.
- **클라이언트 — 박서준 (38, 브랜드 마케터)**: 제품 촬영 작가를 찾는 중. 예쁜 사진보다 "우리 같은 브랜드
  일을 해봤는지"가 궁금하다. *원하는 것*: 비슷한 의뢰 사례를 보고 바로 견적 문의.
- **개인 고객 — 이유나 (29, 웨딩 준비)**: 여러 작가를 비교 중. *원하는 것*: 이 작가의 웨딩 결과물을
  한 흐름으로 보고, 마음에 들면 바로 문의.

## 4. 유저 스토리

- US-1 (작가): 시리즈를 만들거나 수정할 때 **촬영 유형·클라이언트·작업 시기·작업 이야기**를 함께 적어,
  이 묶음이 어떤 일이었는지 남기고 싶다.
- US-2 (방문자): 포트폴리오의 작업 카드를 눌러 **그 작업만의 페이지**에서 맥락과 사진을 끝까지 보고 싶다.
- US-3 (작가): 작업 페이지 **링크 하나**를 고객에게 보내 "이런 작업을 했어요"라고 설명하고 싶다.
- US-4 (방문자): 작업이 마음에 들면 **같은 유형으로 바로 문의**하고 싶다(유형을 다시 고르지 않고).
- US-5 (방문자): 한 작업을 다 보고 나서 **같은 작가의 다른 작업**으로 이어서 보고 싶다.
- US-6 (작가, P1): 포트폴리오 첫 화면에서 방문자가 **촬영 유형별로** 작업을 골라보게 하고 싶다.
- US-7 (작가, P2): 실제 고객 추천사를 **해당 작업에 붙여** 설득력을 높이고 싶다.

## 5. 수용 기준 (AC) — P0 슬라이스

**데이터**
- AC-1: `Series`에 4개 필드가 추가된다 — `shootType`(문의 폼과 같은 어휘 7종 중 하나 또는 비움),
  `clientLabel`(최대 100자, 예: "OO 브랜드", "개인 의뢰"), `shotOn`(`YYYY.MM` 형식 또는 비움),
  `story`(TEXT, 최대 3000자). 기존 시리즈는 모두 비어 있는 상태로 계속 동작한다(순수 추가).
- AC-2: 잘못된 `shootType`·`shotOn` 형식, 길이 초과는 400으로 거절된다. 저장 시 HTML 태그는 제거된다.
- AC-3 (보안): 시리즈 생성 시 요청의 `memberId`가 로그인 사용자와 다르면 403(관리자 제외).
  기존에는 요청의 `memberId`를 그대로 믿어 남의 이름으로 시리즈를 만들 수 있었다.

**작가 화면 (`/series` 시리즈 관리)**
- AC-4: 시리즈 생성/수정 모달에서 4개 필드를 입력·수정할 수 있다. 모두 선택 입력이다.

**공개 화면**
- AC-5: `/portfolio/:profileName/work/:seriesId`에서 커버, 제목, 메타 줄(유형 · 클라이언트 · 시기 · n장),
  작업 이야기, 사진 전체(세로 흐름), 하단 CTA, "다른 작업" 목록이 보인다. 값이 없는 메타는 줄에서 생략된다.
- AC-6: 시리즈가 해당 작가의 것이 아니거나 존재하지 않으면 "작업을 찾을 수 없어요" 화면을 보인다
  (다른 작가의 시리즈를 남의 포트폴리오 주소로 노출하지 않는다).
- AC-7: "이런 촬영 문의하기"를 누르면 `/inquiry/:profileName?memberId=..&shootType=..`로 이동하고,
  문의 폼의 촬영 유형이 미리 선택돼 있다. 유형이 없는 작업은 선택 없이 이동한다.
- AC-8: 기본 템플릿(Editorial)의 컬렉션 카드에 "작업 노트 보기 →" 진입점이 생긴다. 기존 펼침 동작은 유지.
- AC-9: 로딩 중 스켈레톤, 사진이 없는 작업은 빈 상태 안내, 모바일(≤767px)에서 1컬럼으로 깨지지 않는다.
- AC-10: "링크 복사" 버튼으로 작업 페이지 주소를 복사할 수 있다(US-3).

## 6. 우선순위

### P0 — 이번 구현 (컨셉의 최소 증명)
작업 케이스 데이터(AC-1~3) + 작가 입력(AC-4) + 공개 작업 페이지(AC-5~7, 9~10) + 기본 템플릿 진입점(AC-8).
**선정 이유**: 세 기둥(작업 단위·맥락·이어지는 의뢰)을 한 번에 증명하는 가장 작은 단위이고,
새 테이블 없이 기존 `Series`에 컬럼만 더하는 순수 추가라 리스크가 낮다.

### P1 — 다음 (2주)
- 포트폴리오 첫 화면 "작업 유형" 필터 칩(작업이 있는 유형만 노출) — US-6
- 나머지 템플릿(Scrl/Minimal/DarkRoom)에도 작업 페이지 진입점
- 작업 페이지 OG 메타(제목·커버·작업 이야기 앞부분) — 링크 공유 미리보기
- 문의 수신함에 "어떤 작업을 보고 왔는지"(seriesId) 표시 — 문의 엔티티에 `sourceSeriesId` 추가
- 모바일 앱 `SeriesScreen`에 4개 필드 입력

### P2 — 중기
- 추천사를 작업에 연결(`testimonial.seriesId`) — US-7
- "대표 작업" 고정(포트폴리오 상단 1건)
- 작업 페이지에서 예약 위저드로 바로 이동(유형 프리셋)
- 작업 페이지 단위 방문 분석(analytics `targetType=SERIES`)

## 7. 트레이드오프

| 결정 | 대안 | 선택 이유 |
|---|---|---|
| `Series`에 컬럼 추가 | 새 `Project` 엔티티 | 이미 사진 묶음·순서·커버가 Series에 있다. 엔티티를 쪼개면 시리즈/프로젝트 두 개념이 사용자에게 혼란. |
| `shootType`은 문의 폼 어휘(한글 값) 재사용 | 예약의 영문 enum(`WEDDING` 등) | 이번 CTA의 목적지가 문의 폼이므로 같은 값이어야 프리필이 된다. 예약 연결(P2) 때 매핑 테이블 추가. |
| 공개 API 신설 없이 `GET /portfolio/:profileName` + `GET /series/:id` 조합 | 전용 `GET /portfolio/:p/work/:id` | 두 API 모두 이미 공개. 소유자 일치 검사는 클라이언트에서 하되, 노출되는 데이터는 원래 공개된 것뿐이라 보안상 차이가 없다. 트래픽이 커지면 전용 API로 1회 호출화. |
| 작업 이야기는 평문(줄바꿈만) | 리치 텍스트/마크다운 | XSS 표면을 늘리지 않고, "짧고 담백한 캡션" 톤에도 맞다. |
| `shotOn`은 `YYYY.MM` 문자열 | DATE 컬럼 | 일(day)까지 필요 없는 정보이고 `Achievement.yearMonth`와 같은 관례. |

## 8. 성공 지표 (KPI)

- 작업 노트 작성률: 시리즈 중 `story` 또는 `shootType`이 채워진 비율 — 4주 후 40%
- 작업 페이지 → 문의 전환: 작업 페이지 조회 대비 "이런 촬영 문의하기" 클릭률 — 5%
- 문의 폼의 촬영 유형 사전 선택 비율(작업 페이지 경유 문의 중) — 측정 시작 (P1의 sourceSeriesId 이후)

## 9. 자체 검증 (Grill)

- *"시리즈가 없는 작가는?"* → 작업 페이지는 진입점이 없을 뿐, 포트폴리오는 그대로. 손실 없음.
- *"기존 시리즈 데이터는?"* → 새 컬럼은 모두 nullable. 비어 있으면 메타 줄·이야기 영역이 생략될 뿐이다.
- *"남의 시리즈 id를 내 포트폴리오 주소에 붙이면?"* → AC-6, 소유자 불일치 시 not-found 화면.
- *"운영 DB 마이그레이션은?"* → `ddl-auto: update`로 자동 반영되지만 관례대로 CLAUDE.md에 `ADD COLUMN IF NOT EXISTS` 기록.
- *"공수 현실성"* → 백엔드 컬럼 4 + 검증, 프론트 페이지 1 + 모달 필드 4 + 진입점 1 + 문의 프리필. 1일 규모.
- *"모바일은?"* → 이번 P0는 웹 공개 페이지(방문자는 대부분 웹 링크로 들어옴). 모바일 입력은 P1로 명시.

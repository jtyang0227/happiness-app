# claude-md-management — CLAUDE.md 건강 점검 스킬

CLAUDE.md는 이 저장소에서 작업하는 모든 Claude Code 세션이 참조하는 단일 진실 공급원
(source of truth)이다. 매 작업이 끝날 때마다 "작업 완료 규칙"에 따라 새 섹션/불릿이
추가되도록 되어 있는데, 이 누적 과정 자체를 점검하는 도구는 없었다. 이 스킬은 그 공백을
메운다.

**핵심 원칙: 이 스킬은 리포트만 만든다. CLAUDE.md를 직접 고치지 않는다.** 다른 세션들이
지금 이 순간에도 이 파일을 참조하고 있을 수 있는 공유 문서이므로, 발견한 문제를 사람(또는
이 스킬을 호출한 세션)이 검토하고 판단해서 고치게 한다. 사용자가 "찾은 거 다 고쳐줘"라고
명시적으로 요청하면 그때는 리포트를 근거로 하나씩 Edit해도 되지만, 그 요청 없이 먼저
고치러 들어가지 않는다.

## 점검 절차

### 1단계 — 기계적 검사 (스크립트)

`scripts/check_references.py`를 실행해 CLAUDE.md 안의 백틱 참조(파일 경로, `/api/...`
엔드포인트) 중 저장소에 실제로 존재하지 않는 것을 찾는다:

```bash
python3 .claude/skills/claude-md-management/scripts/check_references.py .
```

이 스크립트는 문자열 매칭 기반의 1차 필터일 뿐이다 — "확실히 죽은 참조 후보"를 걸러줄
뿐, 오탐(false positive)이 있을 수 있다(예: 예시로만 언급된 경로, 아직 만들 계획인
파일). 스크립트가 찾아낸 각 후보는 반드시 Read/Glob으로 직접 확인한 뒤 보고서에 넣는다 —
스크립트 출력을 그대로 베끼지 않는다.

### 2단계 — 사람 판단이 필요한 검사 (직접 수행)

CLAUDE.md 전체를 Read로 읽은 뒤, 아래 네 가지를 스스로 점검한다. 각각 근거(줄 번호 또는
인용)를 남긴다.

**(a) 중복/모순 탐지**
- 같은 사실(같은 버그, 같은 API, 같은 설정값)이 서로 다른 섹션에 두 번 이상 적혀 있는가?
- 서로 모순되는 서술이 남아있는가? (예: 이 저장소는 실제로 "이전 방향 폐기" 같은 명시적
  전환 기록을 남기는 관례가 있다 — Toss 디자인 시스템이 AKIRA/Cosmos 방향을 대체하며 남긴
  기록이 좋은 예. 이런 명시적 전환 기록 없이 오래된 서술과 새 서술이 그냥 나란히 남아있으면
  모순으로 본다.)
- 폐기된 디자인 문서(`DESIGN_PROMPTS/deprecated/`)를 여전히 "현재" 방향인 것처럼
  설명하는 대목이 있는가?

**(b) 포맷 일관성**
- 이 파일의 지배적인 관례는 `- **모듈/파일명** — 설명. \`ClassName\` (\`/api/경로\`) —
  동작 설명. **버그 수정**: ...` 형태다. 최근에 추가된 것으로 보이는 항목(작업 이력 언급이
  있는 항목)이 이 패턴에서 벗어나 있으면(예: 불릿이 아니라 산문, 코드 블록 남용, 백틱 없는
  파일명) 지적한다.
- 새 섹션이 기존 섹션 구조(`## 대분류` → `- **하위항목**`)를 따르는지 확인한다.

**(c) 장황함/밀도**
- 한 불릿이 여러 개의 서로 다른 기능·버그 수정을 한 문단에 다 욱여넣어서 스캔하기
  어려워졌는가? (이 파일은 이런 경향이 이미 있다 — 하나의 컴포넌트 설명 불릿에 버그 수정
  이력 3~4개가 붙어 300단어를 넘는 경우가 실제로 있다.) 이런 불릿은 "핵심 동작 요약 + 버그
  수정 이력 분리" 같은 구체적인 리팩터링 안을 제안한다. 다만 이 파일의 정보 밀도 자체가
  의도된 설계(다른 세션이 이 파일 하나만 읽고 전체 맥락을 얻도록)이므로, 정보를 삭제하라고
  제안하지 않는다 — 재구성/분리만 제안한다.
- 섹션 하나가 너무 커져서 하위 파일로 쪼개는 게 나아 보이면(예: 특정 기능군이 너무 커짐)
  제안하되, 이 저장소가 지금까지 단일 CLAUDE.md 파일을 유지해온 것도 의도적 선택임을
  존중해 "강제 이관"이 아니라 "고려해볼 만한 옵션"으로 제시한다.

**(d) 모바일/웹 형평성 체크** (이 저장소 특유의 반복 패턴)
- 이 프로젝트는 웹에서 먼저 만들고 모바일에 나중에(또는 영영 안) 반영하는 패턴이 잦다.
  최근 웹 전용으로 추가된 기능 중 "모바일은 아직 미반영"이라는 명시적 언급이 없는 게
  있으면 짚어준다 — 실제로 빠뜨리기 쉬운 지점이다.

## 보고서 형식

찾은 것이 있든 없든 아래 형식으로 보고한다. 항목이 없는 카테고리는 "없음"이라고 명시한다
(조용히 생략하지 않는다):

```
## CLAUDE.md 점검 결과

### 죽은 참조 (기계 검사 + 직접 확인)
- [파일/경로] — CLAUDE.md 몇 번째 섹션에서 언급, 실제로는 없음/이동함 → 어떻게 됐는지

### 중복/모순
- [설명] — 두 위치(섹션명 인용) 비교

### 포맷 이탈
- [설명] — 몇 번째 섹션, 어떤 관례에서 벗어났는지

### 장황함
- [섹션명] — 왜 나눠야 하는지, 어떻게 나누면 좋을지 구체적 제안

### 모바일/웹 형평성
- [기능명] — 웹만 있고 모바일 언급 없음

---
CLAUDE.md는 수정하지 않았습니다. 위 항목 중 반영을 원하시는 게 있으면 말씀해주세요.
```

## 하지 말 것

- 사용자가 요청하지 않았는데 CLAUDE.md를 먼저 Edit하지 않는다.
- 스크립트의 오탐(false positive)을 검증 없이 그대로 "죽은 참조"라고 보고하지 않는다 —
  반드시 Read/Glob으로 직접 확인 후 보고한다.
- 이 파일의 높은 정보 밀도 자체를 "문제"로 규정하고 대량 삭제를 제안하지 않는다 — 이 파일은
  일부러 상세하게 쓰여 있고, 그게 이 저장소의 설계 의도다. 문제는 밀도가 아니라 죽은 정보,
  중복, 포맷 붕괴다.

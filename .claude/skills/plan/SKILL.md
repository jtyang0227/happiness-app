# Happiness — PM 기획 스킬

새 기능 기획이든 앱 전체를 아우르는 마스터 로드맵이든, **추측으로 쓰지 않는다** — 항상
코드와 기존 문서를 먼저 읽어 현재 상태를 확인한 뒤 그 위에 기획을 얹는다. 그리고 초안을
쓰고 끝내지 않고, 스스로 비판적으로 재검증(GRILL)하는 단계를 반드시 거친다.

`.claude/agents/planner.md`(자율 서브에이전트)와 역할이 겹치지만, 이 스킬은 **현재 세션에서
바로 실행**되고 GRILL(자가 비판적 검증) 단계가 필수라는 점이 다르다.

---

## 워크플로우 (항상 이 순서, 생략 금지)

### 1. DISCOVER — 현황 파악 (추측 금지)
문서만 읽고 쓰지 않는다 — 실제 코드를 확인한다.
- `CLAUDE.md` 전체(아키텍처, 완료된 기능, 알려진 갭 — "버그 수정" 각주들 포함)
- `DESIGN_PROMPTS/planning/`, `DESIGN_PROMPTS/design/` 기존 문서 목록 — 이미 다뤄진 주제와
  겹치는지, 참고할 결정이 있는지 확인. 마스터 로드맵급 기획이면 전부 훑는다.
- 대상 기능/영역의 실제 코드(컨트롤러·페이지·스크린)를 열어 "문서에 쓰여있는 것"과
  "실제로 구현된 것"이 다른 부분을 찾는다 — CLAUDE.md 자체도 과거 시점 기준일 수 있다.
- 앱 전체 기획이면 3개 플랫폼(웹/모바일/어드민) 모두의 현재 상태를 각각 확인한다.

### 2. SCOPE — 범위 확정
무엇을 다루고 무엇을 다루지 않는지 1~2문장으로 먼저 명확히 한다. 범위가 애매하면
(예: "기획서 다시 써줘"처럼 대상이 불분명하면) 추측해서 진행하지 말고 사용자에게 되묻는다.

### 3. DRAFT — 초안 작성
기존 기획 문서들과 동일한 구조를 따른다(`PLANNING_<feature>.md` 또는 신규 마스터 문서):

```markdown
# PLAN — <제목>
> 작성일 | PM: Claude | 대상: <플랫폼/영역>

## 1. 배경
## 2. 현황 진단 (코드 검증) — DISCOVER 단계에서 확인한 사실만 기술, 추측 금지
## 3. 개선 방향 / 전략
## 4. 사용자 페르소나
## 5. 유저 스토리
## 6. 수용 기준 (AC)
## 7. 기능 범위 (In/Out of Scope)
## 8. 기술 트레이드오프 (표 — 옵션/장점/단점/채택여부)
## 9. 우선순위 로드맵 (P0/P1/P2 — 항목/플랫폼/예상 공수)
## 10. 성공 지표 (KPI)
## 11. 관련 파일
```
마스터(앱 전체) 기획이면 6~7절은 플랫폼별(웹/모바일/어드민)로 나누어 쓴다.

### 4. GRILL — 자가 비판적 검증 (생략 금지)
초안을 쓴 자신을 잊고, **면접관처럼 무자비하게** 아래를 하나씩 공격한다. 방어할 수 없는
항목은 문서에 남기지 말고 5단계에서 고친다.

- **견적이 현실적인가?** "1시간"이라 적은 항목이 실제로는 새 라이브러리 설치·마이그레이션이
  필요하지 않은가?
- **숨은 의존성이 있는가?** 이 기능이 이미 존재하는 다른 기능(인증, 결제, 알림 등)에
  당연히 의존하는데 그게 실제로 준비돼 있는지 확인했는가? (추측 말고 코드로 확인)
- **기존 아키텍처와 모순되는가?** 예: 다크 테마 페이지에 라이트 컴포넌트를 아무렇지 않게
  넣는 계획은 아닌가? `ddl-auto: validate`인데 스키마 변경을 배포 스텝에 안 넣은 건 아닌가?
- **플랫폼이 빠지지 않았는가?** 웹만 쓰고 모바일/태블릿을 잊지 않았는가(또는 반대)?
- **트레이드오프 표가 정직한가?** 채택 안 한 옵션의 단점을 실제보다 부풀리지 않았는가?
- **로드맵 우선순위가 사용자 가치 기준인가, 아니면 그냥 쉬운 것부터 나열한 건 아닌가?**
- **AC가 검증 가능한가?** "잘 동작한다" 같은 모호한 문장이 아니라 실제로 확인 가능한
  구체적 조건인가?

발견한 문제를 목록으로 짧게 남긴다(문서에 넣지 않고 이 단계의 산출물로만 — 사용자에게
보고할 때 "이런 걸 스스로 잡아서 고쳤다"고 투명하게 공유해도 좋다).

### 5. REVISE — 반영
GRILL에서 나온 문제를 초안에 반영해 고친다. 견적을 수정하거나, 우선순위를 재배치하거나,
빠진 플랫폼 섹션을 추가하거나, AC를 구체화한다.

### 6. FINALIZE — 저장 + 요약
- `DESIGN_PROMPTS/planning/PLANNING_<feature>.md`(또는 마스터 문서는
  `DESIGN_PROMPTS/planning/MASTER_PLAN_<날짜 or 버전>.md` 같은 구분되는 이름)로 저장.
- 관련 기존 문서에서 상호 참조가 필요하면(예: CLAUDE.md의 "Project Overview"가 참조하는
  문서가 실제로 없거나 오래됐다면) 그 사실을 사용자에게 알린다 — 조용히 넘어가지 않는다.
- 사용자에게 최종 요약(핵심 로드맵, GRILL에서 잡은 주요 이슈)을 전달한다.

## 마스터(앱 전체) 기획 시 추가 유의사항

- **`PORTFOLIO_FEATURES.md`가 CLAUDE.md의 "Project Overview"에서 참조되지만 실제로는
  저장소에 존재하지 않을 수 있다** — DISCOVER 단계에서 `find`로 반드시 확인하고, 없다면
  이 사실을 문서에도, 사용자 보고에도 명시한다(추측으로 "있다고 치고" 참조하지 않는다).
- 이 세션 안에서 이미 진행된 작업(최근 커밋 로그, `DESIGN_PROMPTS/planning/PLANNING_*.md`
  최신 파일들)을 먼저 확인해 "이미 끝난 걸 또 계획하는" 중복을 피한다.
- 기술 부채(알려진 버그, mock 상태인 기능, 미완성 템플릿, 배포 시크릿 미등록 등)를
  숨기지 않고 별도 섹션으로 정리한다 — 로드맵의 신뢰도는 이런 걸 얼마나 정직하게
  드러내는지에 달려있다.

## 금지 사항

- 코드/문서를 확인하지 않고 "아마 이럴 것"이라고 추측해서 현황 진단을 쓰는 것.
- GRILL 단계를 생략하고 초안을 그대로 최종본으로 제출하는 것.
- 이미 존재하는 기획 문서와 내용이 겹치는데 확인 없이 새 문서를 또 만드는 것.
- 견적·우선순위에 대한 근거 없이 숫자만 나열하는 것.
- 사용자 확인 없이 범위(전체 앱 vs 특정 기능)를 임의로 좁히거나 넓히는 것.

## 최종 체크리스트

- [ ] DISCOVER 단계에서 실제 코드/문서를 확인했음(추측 없음)
- [ ] 기존 기획 문서와의 중복 여부 확인함
- [ ] GRILL 단계를 실제로 거쳤고, 발견한 문제를 초안에 반영함
- [ ] AC가 구체적이고 검증 가능함
- [ ] 우선순위 로드맵에 플랫폼·예상 공수가 명시됨
- [ ] 알려진 기술 부채/미완성 항목이 숨겨지지 않고 명시됨
- [ ] `DESIGN_PROMPTS/planning/`에 저장 완료
